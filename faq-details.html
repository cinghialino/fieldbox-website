How Fieldbox verifies each copy

How verification works

Think of it like a wax seal on a letter. The seal is made from the exact contents of what's inside, so if a single word changes, the seal no longer matches. Fieldbox does the same thing with a mathematical fingerprint (the technical name is SHA-256) instead of wax.

  1. Fieldbox reads the file straight off your card and calculates its fingerprint.
  2. It copies the file onto your device.
  3. It reads the copy back and calculates the fingerprint again.
  4. The two fingerprints are compared. If they match exactly, the file is marked verified. If they don't, Fieldbox retries the file once before flagging it as failed.

This happens for every selected file in the transfer, not a sample. The green "all files verified" screen appears only after every selected file has been copied and its source and local fingerprints have been compared and matched. Files shown as already verified or deliberately excluded are accounted for separately.

How Fieldbox confirms a cloud backup really landed

Uploading a file and having the upload finish without an error isn't proof the file is intact, connections drop, bytes get corrupted along the way, and a naive app would show "done" anyway. Fieldbox records the strongest confirmation each provider can actually supply.

  1. Your device always checks the copy. Every local archive file is SHA-256 verified against the card before Fieldbox keeps it.
  2. Cloud checks depend on the provider. Fieldbox records a matching provider-reported checksum where one is available. Otherwise it records provider acceptance or object existence together with the expected stored size.
  3. Fieldbox checks back afterward. After an upload, Fieldbox asks the provider for the file's stored size and, where the provider supports it, its checksum. The app labels an upload receipt separately from cloud hash verification.

A cloud backup only shows as upload-confirmed once the provider's available check passes for every file. The local archive records matching source and local SHA-256 values; cloud hash verification is called out only where the provider supplies a matching checksum.

Why a file can take a few minutes to appear in your cloud provider's website

A provider's web file browser can take time to display a newly uploaded object. Fieldbox checks that specific object using the confirmation method available from the provider and records the response separately from what may be visible in the provider's listing interface.

How shared cloud accounts stay organized

Sharing one cloud login across a crew needs clear ownership boundaries. Fieldbox assigns each device its own top-level namespace and applies session-based controls when Cloud Browser is opened from a session.

Separate device namespaces keep identical camera filenames from sharing the same cloud object path. A device can browse shared-account inventory, while deletion controls are limited to the current device's top-level area.

This is FieldBox Core storage behavior, not a Pro feature. Within Fieldbox, deletion controls cannot remove another installation's top-level area.

What happens when a transfer is interrupted

If you interrupt a transfer, close the app, unplug the reader, or lose power, Fieldbox preserves only the files that completed local verification.

A file is promoted into the archive only after its local verification succeeds. After an interruption, Fieldbox records which files were verified and which still need attention. Nothing on the card is changed by the app, and verified files are not copied again when the transfer continues.

The screen tells you how many files completed verification before the interruption. To continue, reconnect the source and choose it in Files. Fieldbox checks the recorded card identity, selected folder, current inventory, and per-file checkpoints before it resumes, then skips files whose completed checkpoints still match. You can also discard the interrupted transfer and its partial local files.
