How Does FieldBox Know? Designing Evidence for Field Backup

A check performed by Fieldbox, a confirmation returned by a storage provider, a source scan, and a fact reported by a person are not the same thing. A useful backup record should say where each claim came from.

Alessandro CasagliAugust 3, 20268 min read

Backup software has a language problem. A single green checkmark can mean that an app compared two files, that a server accepted an upload, or simply that no error appeared. Those are different facts, supported by different evidence.

Fieldbox is built for decisions made away from a computer, often while the original memory card is still part of the working set. In that situation, a status is only useful when the person reading it can answer a more basic question:

How does FieldBox know this?

That question led to four evidence-source labels. They do not form a ladder from unsafe to safe. They identify who or what supplied the evidence, what was actually checked, and where the limits are.

Verified by FieldBox

Fieldbox directly performed the relevant comparison or reread current bytes and matched them to the recorded manifest.

Confirmed by destination

A configured storage destination supplied evidence about the object it stored.

Observed during scan

A complete, read-only scan saw attributed originals at a recorded point in time.

Reported by user

A person supplied a source-status fact that Fieldbox could not independently inspect.

Verified by FieldBox

During an import, Fieldbox reads a file from the source card and calculates its SHA-256 value. It then reads the staged local copy and calculates that value again. Only a match is promoted into the app-managed archive.

That is a check Fieldbox performed, so it belongs under Verified by FieldBox. A later local integrity check can also reread current archive bytes and compare them with the recorded manifest.

The wording stays deliberately narrow. It says which values matched when the check ran. It does not promise that a device will remain available or that a file can never be changed or lost later.

Confirmed by destination

Cloud and NAS storage sit across a service boundary. Fieldbox asks the configured destination what it stored, then records the strongest usable evidence that destination exposes.

Some destinations can return a matching SHA-256 checksum. Others confirm that an object was accepted or exists with the expected stored size. Both are destination evidence, but they are not interchangeable. The interface must retain the precise method rather than turning every successful upload into “cloud hash verified.”

This is why the broad label is Confirmed by destination. It attributes the statement correctly while leaving room to say whether the confirmation was a provider checksum or acceptance, existence, and size.

Observed during scan

A memory card can change after an import. Files may be removed, the card may be reused, or only part of its earlier contents may remain. A later complete, read-only scan lets Fieldbox compare what it sees with the originals previously attributed to that source.

If 41 of 50 attributed originals are found, Fieldbox can report 82% source coverage observed during that scan. The observation time matters. Once the card is disconnected, Fieldbox cannot claim that its contents remain unchanged.

Coverage can be partial, but counting a source as one complete current copy remains binary: the applicable complete scan must have observed every attributed original.

Reported by user

Sometimes the source is no longer connected and Fieldbox cannot inspect it. A person may report that the originals are no longer available. Fieldbox records that change in the Events Log and labels it Reported by user.

This is not a failed verification, and it is not presented as a measurement. It is a useful fact with an explicit origin.

If a later scan finds known originals, the new observation can replace the report as the current evidence while the earlier event remains in the audit history. That does not mean the user was wrong. It means Fieldbox received newer, directly observed information.

One session, four sources of evidence

A single session can contain all four classifications without contradiction:

Local archiveVerified by FieldBox · source and local SHA-256 matched
Offsite copyConfirmed by destination · provider checksum or stored-object evidence stated precisely
Source cardObserved during scan · 41 of 50 attributed originals
Source availabilityReported by user · recorded in Events Log

None of those lines needs an unexplained “trust me” checkmark. Each names the fact, its origin, and—where it matters—the method and time behind it.

Where the Integrity Record fits

An Integrity Record freezes a point-in-time view of a session. It binds the session identity, the verified-file manifest, and explicit evidence methods in a deterministic payload. Its signed envelope lets a verifier detect changes to that payload and compare records associated with the same device-held signing key.

The signature does not turn an observation into a broader claim. It does not establish civil identity, trusted time, external certification, legal authentication, or the continued existence of a file after the recorded check. A screenshot is a visual rendering; the signed data is the verifiable artifact.

The current record format also has a deliberate boundary: partial live source coverage cannot be placed into its existing source-card status without changing the schema. The live interface can explain current observations while the versioned record keeps its defined meaning.

What these labels do not claim

They do not certify that files are safe, permanent, or guaranteed recoverable. A provider confirmation does not prove permanent integrity. Fieldbox records what it measured, observed, received, or was told at the applicable time so that the next decision can be made from stated evidence rather than an unexplained status.

A design language, not a marketing badge

The value of this model comes from using it consistently. Backup Status, File Source Ledger, Events Log, Transfer Details, and Integrity Verification should not invent separate words for the same evidence origins.

Over time, the labels become a compact design language. “Verified by FieldBox” means the app performed the check. “Confirmed by destination” means the storage system supplied the evidence. “Observed during scan” remains tied to an observation. “Reported by user” remains a recorded human statement.

Say what was checked, who supplied the evidence, and when it was observed—without turning those facts into certainty they cannot support.
