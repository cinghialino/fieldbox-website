Field Notes · Transfer design

Every File Needs an Outcome

A source scan should not collapse into a single copied count. Fieldbox accounts for what will transfer, what was already present, what was excluded, and what remains unfinished, then freezes that decision before any bytes move.

Alessandro CasagliAugust 6, 20268 min read

Most transfer screens begin with a folder and end with a progress bar. Between those two moments, a surprising amount of meaning can disappear.

A card might contain RAW files, matching JPEGs, video, audio, sidecars, camera databases, and files with extensions the app has never seen. Some may already be verified in the chosen session. Some may be intentionally left out. If the interface reports only “37 files to copy,” the person using it cannot tell what happened to everything else the scan found.

That ambiguity matters on location. Before starting a transfer, the useful question is not only “how many files will move?” It is “what is the outcome for every file Fieldbox discovered?”

A scan becomes a transfer plan only when every discovered file has an explicit outcome.

Selection starts with what the scan found

Fieldbox groups the scanned files by capture date so the review begins with a recognizable view of the work. A person can select an entire date, open that date to choose individual files, or select everything before continuing.

The selection is visible and deliberate. A file can be left out, but it does not disappear into an unstated rule. Files outside the selection are excluded from this transfer rather than being reported as failures or verified results.

01ScanEnumerate the selected source without modifying it.
02GroupPresent the scanned files by capture date.
03SelectChoose whole dates or individual files.
04FreezeRecord the exact selected, skipped, and excluded disposition.

The result is a review that can state a complete equation: every scanned file is either selected for transfer, recognized as already verified in that session, or explicitly excluded. Those groups are disjoint, and together they account for the scan.

Counts and bytes belong together

A file count alone can be misleading. Ten small sidecars and ten large video clips place very different demands on the device and its destinations. Fieldbox therefore calculates both counts and bytes from the same cached selection snapshot.

That same selected-byte total drives the storage review. The device check retains 1 GB of free-space headroom. Each chosen cloud or NAS destination gets its own card and, where the provider reports capacity, its own comparison with the selected size.

Provider capacity is advisory evidence. Some destinations report used and total storage, some report no quota, and a capacity request can be unavailable. Fieldbox keeps those states distinct instead of converting “not reported” into “enough space.” A favorable capacity report also does not confirm that an upload has happened. It only informs the decision before it starts.

Preflight

What the transfer intends to do

Selected counts and bytes, prior-import skips, explicit exclusions, device headroom, and provider-reported capacity.

Outcome

What the transfer actually established

Per-file copy and verification results, plus the exact destination evidence recorded after later uploads.

Keeping preflight and outcome separate prevents an intention from being mistaken for evidence. Selecting a destination is not confirmation. Estimating space is not a completed copy. Reaching the end of a copy operation is not verification.

The plan is frozen before copying

Once the user starts, Fieldbox persists the transfer plan before processing the first selected file. The plan includes source identity, selected-root identity, a deterministic digest of the complete path-and-size inventory, the selected files, and the scan disposition.

Freezing the plan serves two purposes. First, the completion view and later transfer details can explain the same decision that was reviewed at the beginning. Second, an interrupted transfer has a stable definition of what remains to be done.

Excluded files are summarized by category or unfamiliar extension, count, and bytes. They are not presented as failed files, and they are never described as verified. The record preserves the decision without borrowing stronger language from the files that actually passed comparison.

Interruption becomes durable work

A removable source can disappear during a transfer. The reader can be unplugged, the app can leave the foreground, or the device can stop the process. Treating that event as an ordinary failure would discard useful facts about files that already completed.

Fieldbox writes a durable checkpoint after each file is copied, read back, and found to have the same SHA-256 value as its source. If the source goes away, those checkpointed files remain identified as completed within an unfinished transfer. The remaining selected files stay pending.

  • A checkpoint is written only for a file whose source and local SHA-256 values matched.
  • An interrupted transfer is not shown as complete.
  • The frozen scan disposition remains attached to the same transfer.
  • The source card is read but never modified, erased, formatted, or ejected by Fieldbox.

Resume must identify the same source state

A matching folder name is not enough to resume. Another card can contain familiar names and similar sizes. Fieldbox requires the reconnected volume identity, selected-root identity, and complete path-and-size inventory to match the frozen plan before it claims the recovery work.

It then checks that every checkpointed source file still has the recorded SHA-256 value. The corresponding archive paths are also revalidated. A current verified archive file is kept. If an archive file at a checkpointed path has changed, Fieldbox removes only that stale local file and its sidecar so the planned file can be copied and verified again at the recorded path.

Only after those checks does the transfer continue. Files whose verified archive copies are still current are not copied again. Pending files, and any checkpoint whose local bytes no longer match, return to the ordinary stage, compare, and promote sequence.

Resume is not “try the folder again.” It is “continue this frozen plan from the same measured source inventory.”

A completion screen should reconcile the beginning and the end

When the transfer finishes, the final record can be checked against the plan. The selected file count must match the file records, selected bytes must reconcile with their sizes, every selected file must have a verified result, and the manifest commit must be durable.

This makes success narrower and more useful. Previously imported files were not copied again. Excluded files were not verified. Provider capacity was not upload confirmation. The success statement belongs only to the selected files whose measured source and local SHA-256 values matched and whose records were committed.

The boundary of the claim

Explicit accounting explains what Fieldbox found and what happened during this transfer. Checkpoints preserve measured progress. Neither one guarantees future availability or recoverability. Later device checks and destination confirmations remain separate evidence about the current copies.

Clarity is a reliability feature

None of these mechanics makes copying visually dramatic. Most of the work appears as better nouns, clearer counts, separate destination cards, and an interrupted state that refuses the wrong source.

That restraint is the point. A field-backup tool should not make a person infer what happened from a progress bar. It should expose the decision before copying, preserve that decision while work is underway, and reconcile it with the measured result at the end.

Every scanned file should have an outcome, and every outcome should keep the limits of its evidence.

A quick note: This is how Fieldbox handles transfer accounting and interrupted transfers today. It explains what the app records, not a promise that files will always remain available.
