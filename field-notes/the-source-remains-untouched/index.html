Field Notes · Source design

The Source Remains Untouched

Fieldbox needs to read the source closely enough to verify a copy. It does not need to take control of the source’s lifecycle.

Alessandro CasagliJune 19, 20267 min read

Backup tools often drift toward media management. Once an app can read a card, offering to erase it, format it, or eject it after a transfer can look like a natural convenience.

For Fieldbox, that convenience would cross an important boundary. The source is not part of the archive the app manages. It belongs to the user and may still be the only location for a file that failed, was skipped, or has not reached another complete destination.

The decision was made early: Fieldbox can inspect the source, but it does not change it.

The app may produce evidence about the source. It does not take ownership of the source.

Reading is necessary; control is not

Fieldbox recursively scans the selected source, reads file metadata, copies bytes into local staging, and calculates SHA-256 from the source file. Those operations are necessary to create and verify another copy.

Erasing, formatting, deleting, modifying, or ejecting are different categories of action. None is necessary to verify a transfer. Keeping them outside Fieldbox makes the app’s relationship with the source easier to state and easier to audit.

  • Fieldbox does not erase or format the source.
  • Fieldbox does not modify or delete source files.
  • Fieldbox does not eject the source.
  • Source scans that update coverage are read-only.

The boundary applies whether the removable media came from a still camera, cinema camera, audio recorder, drone, or another field device. The user may have a very different reuse workflow for each. Fieldbox does not need to own any of them to report what it copied and verified.

A failed file makes the distinction visible

Consider a transfer in which every file except one passes local verification. Fieldbox can keep the verified files already promoted into the archive and identify the failed file precisely.

If the same app also offered to clear the card, it would have to turn that evidence into a destructive recommendation. The product would move from “this file did not pass” to “the source may now be erased,” a much broader conclusion involving every other copy and every later dependency.

Fieldbox stops before that leap. A failure remains visible, the source remains unchanged, and the media decision stays with the person responsible for it.

Why there is no “safe to format” state

A green inventory can summarize measured conditions: all verified files are present on the device, a complete provider is confirmed offsite, and the current copy count meets Fieldbox’s defined 3-2-1 rule.

That still does not make the app the authority over what happens next. Provider state can change, devices can fail, business requirements differ, and the user may have reasons to keep original media beyond the copy inventory Fieldbox knows about.

So the interface reports the inventory and leaves the decision separate. It does not convert a current status into permission to reuse the source.

Fieldbox reports

What the app measured or recorded

Source/local hash matches, current source observations, provider evidence, and the resulting copy inventory.

The user decides

What happens to the original media

Whether and when to erase, format, eject, archive, retain, or reuse the source.

Source status is evidence, not remote control

The source can change outside Fieldbox. It may be reused in a camera, edited by another device, damaged, or simply disconnected. The app cannot keep making a live claim about media it can no longer inspect.

When connected, a complete read-only scan can record which previously attributed originals were observed. When disconnected, the user can report that the originals are no longer available. Fieldbox labels that fact Reported by user and records it in the Events Log rather than presenting it as a measurement.

If a later scan sees known originals again, the newer observation can update the current source evidence while the earlier report remains part of the history. The source still has not been changed by Fieldbox; only the app’s account of available evidence has changed.

Rejecting the helpful sidecar

Writing a small tracking file to the source could make recognition easier. It could carry a session identifier or note which files had already been imported. The write might appear harmless compared with formatting a card.

It would still break the rule. A source that was read-only before Fieldbox arrived would leave with a Fieldbox-created file. It could also interact with camera expectations, media-lock switches, filesystem permissions, or another user’s archival policy.

The current design accepts the harder identity problem and keeps its evidence on the device. Convenience does not quietly expand the app’s authority.

The boundary of the claim

Fieldbox can state that it did not erase, format, modify, delete from, or eject the source and can describe what a read-only scan observed. It does not decide that a source is safe to erase or guarantee what will remain recoverable afterward.

Restraint is part of reliability

Reliability is often described as doing more: more automation, more recovery, more safeguards. In this case, reliability also comes from refusing an operation the core workflow does not require.

The source gives Fieldbox the bytes against which a new copy is measured. Keeping that source outside the app’s destructive control preserves a clear division of responsibility. Fieldbox makes copies, compares them, records evidence, and reports the current inventory. The source remains the user’s.
