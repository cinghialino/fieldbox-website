The Boundaries of an Integrity Record

A signed record becomes more credible when it is precise about what the signature binds and equally precise about everything the signature cannot establish.

Alessandro CasagliJuly 24, 20269 min read

The first instinct was visual. A session summary could gather its file count, hashes, destinations, and timestamp into one screen. Someone could take a screenshot and share a compact account of what Fieldbox had recorded.

That would be useful presentation, but it would not be a verifiable artifact. Pixels can be edited. Decorative patterns can be reproduced. A timestamp shown on screen can come from an adjustable device clock. Making the screen harder to imitate would not change those facts.

The design turned away from visual authenticity and toward a more modest goal: build a deterministic record of the app’s evidence, sign exactly that record, and make the limits part of the format.

The signature should protect the meaning of the record, not inflate the meaning of its claims.

Four layers, four responsibilities

The Integrity Record became easier to reason about once it stopped trying to be the screen, the signature, and the exported file at the same time. Fieldbox separates those responsibilities into layers.

Integrity RecordThe canonical point-in-time payload: session identity, verified manifest root, copy evidence, timestamps, and current inventory summary.
Signed envelopeThe record plus its payload digest, signature, key identifier, and self-issued verification certificate.
TransportThe deterministic .fieldbox.json bytes used to store or share the envelope.
PresentationThe human-readable screen or any future rendering. Useful for reading, but not the cryptographic artifact.

This separation lets the interface evolve without changing what was signed. It also lets an independent verifier reconstruct the canonical record bytes rather than trusting how a particular screen chose to display them.

The manifest root identifies the verified set

At the center of the record is a SHA-256 root calculated from a canonical list of verified files. Each entry binds its source path, archive destination, byte count, and SHA-256 value. The list is sorted deterministically before the root is calculated.

That root describes which verified-file manifest the record refers to. It does not change because a local file is later deleted, a provider becomes unavailable, or someone reports that a source was reused. Those are later evidence about current copies, not changes to the identity of the historical verified set.

Keeping the distinction matters. If every inventory change rewrote the manifest root, the record would lose a stable subject. Instead, the record binds a stable verified set to a point-in-time account of where Fieldbox currently believes copies exist and how it obtained that evidence.

What the device signature adds

Fieldbox signs the canonical record with a persistent P-256 key held by the device. Supported physical devices use a Secure Enclave key. The Simulator or hardware without that support uses a software key protected in the Keychain, and the envelope discloses which path was used.

A verifier can check the envelope offline using the public material carried inside it. If the signed payload changes, verification fails. Records carrying the same key ID can also be recognized as having been signed by the same locally held key.

Those are meaningful properties, but they stop at the key. The current certificate is self-issued. It proves control of the matching private key; it does not prove that Fieldbox, Apple, a certificate authority, or any other institution certified the device or its owner.

The signature establishes

Payload integrity and key continuity

The canonical record has not changed since that key signed it, and matching key IDs connect records to the same locally held key.

The signature does not establish

Identity, authority, or permanence

It does not certify a person, create trusted time, or show that recorded files still exist after the observation.

A UTC timestamp is not automatically trusted time

The record freezes an observation time so its evidence does not appear to update while someone reads the screen. Current records obtain that time from the device clock and say so.

Expressing the value in UTC makes it unambiguous as a timestamp format. It does not make the clock independent or tamper-resistant. Trusted time would require a separate authority and proof, with its own availability, privacy, and lifecycle decisions.

The format reserves room for future evidence methods, but a reserved value is not a promise that such a service exists.

The negative space is part of the design

Security artifacts often become less trustworthy when their presentation implies more than their mechanism can support. Fieldbox therefore treats the “does not prove” list as part of the architecture, not as legal copy added afterward.

  • No claim of the user’s civil or legal identity.
  • No Fieldbox, Apple, or external certification of the signing key.
  • No independently trusted time from the current device-clock timestamp.
  • No claim that files or provider objects still exist after observation.
  • No forensic-process certification or legal authentication.
  • No cryptographic authenticity claim for a screenshot.

These limits do not weaken the record. They make its positive claims testable. An independent verifier knows exactly what to reconstruct, which signature to check, and which conclusions remain outside the result.

Why the screenshot still exists

People need a readable view. The Integrity Verification screen translates the record into a form that can be inspected quickly, discussed with a client or colleague, or captured for ordinary communication.

The screen and the signed file serve different audiences. The screen helps a person understand the evidence. The `.fieldbox.json` artifact lets software verify that the canonical record has not changed. A screenshot can show the first, but it cannot substitute for the second.

The boundary of the claim

A valid signed envelope shows that its canonical record has not changed since the corresponding device-held key signed it. It does not establish external identity, trusted time, ongoing file existence, legal authentication, or certification.

Precision creates room to evolve

Future systems could bind a key to an account, add independent timestamps, publish revocation information, or preserve records through an external service. Each would introduce new claims and new tradeoffs. None needs to be smuggled into version one.

By keeping today’s boundary narrow, Fieldbox can preserve old records and evaluate future additions honestly. The Integrity Record is useful because it binds a defined set of evidence. It remains credible because it refuses to become a certificate for things it never measured.
